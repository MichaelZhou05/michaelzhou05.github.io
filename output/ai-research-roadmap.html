The big picture

There are two models in a research run. The large researcher writes and tests ideas. The small test model is what it trains. We score the researcher by how much it improves that small model within the rules.

Track A · Model league

Which model is the best researcher?

Keep the agent code, instructions, tools, task, and budget fixed. Swap only the researcher model.

Start with two available model versions. Save exact IDs and settings so later comparisons are meaningful.

Track B · Agent league

Can our agent use the same model better?

Keep the researcher model and task fixed. Compare the pinned autoresearch baseline with our own research loop.

Record both the instructions and the tool runner. program.md alone is not the whole agent.

First goal: complete a fair comparison and publish the results. Beating the baseline is the aim, not a result we can promise. A clear account of what failed is useful work too.

The build plan

Steps 0–3 form the first release. Steps 4–5 add depth. Each effort range is a rough planning estimate for focused work, not a deadline; GPU queues and setup can add time.

0

Prove we can run one experiment

1–2 work sessions

Get one clean autoresearch training run working on Duke compute before building the league.

Build

A pinned copy of the repo, a working environment, and one saved baseline result.

Learn

How a training loop works, what its score means, and how to run GPU jobs.

Concrete steps
  1. Check Duke H200 access, GPU-hour limits, job length, storage, and whether jobs can call model APIs.
  2. Pin an autoresearch commit and record the Python, library, GPU, and driver versions.
  3. Run the unchanged training script. Save logs, runtime, peak GPU memory, and validation score.
  4. Repeat it to estimate how much the score varies without any agent edits.
  5. If compute access is delayed, build the runner with a cheap mock task; defer training claims.
Done when: we can rerun the baseline and explain the inputs, score, and normal run-to-run noise.
1

Build the shared run system

3–5 work sessions

Add one research task to the existing benchmark. Reuse what works; keep new parts small.

Build

A task adapter, run log, score file, and a page that shows the code changes and results.

Learn

Eval design, job control, clean records, and how to keep failed runs from disappearing.

Concrete steps
  1. Review the existing benchmark code and identify reusable model clients, job tools, and UI pieces.
  2. Give each run a task version, agent version, model ID, seed, budget, and unique run ID.
  3. For each experiment, save the proposed change, code diff, logs, score, wall time, GPU time, and API usage.
  4. Run edits in isolated jobs with limits. Keep scoring code and final test data outside the agent's write access.
  5. Make a run page that shows the starting score, each attempt, failures, and the best valid result.
Done when: a successful run and a failed run both leave complete, readable records.

Carry forward: every later project uses the same run IDs, logs, score format, and replay page.

2

Launch the model league

3–5 sessions + GPU runs

Ask two researcher models to improve the same small training setup using the pinned baseline agent.

Build

A small, fair comparison with score-over-time plots and experiment replays.

Learn

Fair budgets, repeated trials, model behavior, and the difference between a lucky win and a stable gain.

Concrete steps
  1. Start with two available, pinned model versions, one task, and three independent runs per model as a pilot.
  2. Use a proposed starting cap of 12 experiments per run, with five minutes of training per experiment on the same GPU type. Adjust once after the smoke test, then freeze the rules.
  3. Set the same tool access, timeouts, and maximum API spend per run. Report actual cost and elapsed time separately.
  4. Include the unchanged training code and a small random search over training settings as baselines.
  5. Pick each run's best candidate using validation data. Score it once on an untouched final test set.
  6. Show all runs, including failures. Add more repeats before making a close ranking claim.
Done when: the comparison can be rerun, all costs are visible, and the report states what the small sample can and cannot show.

Pilot budget: 2 models × 3 runs × 12 attempts × 5 minutes = up to 6 hours of training. Baselines, setup, final tests, and agent thinking add time; API calls have a separate cost.

3

Build our research agent

4–7 sessions + GPU runs

Use the same model to test whether better notes, planning, and checks produce better research.

Build

A simple loop: read past runs → choose an idea → edit → test → keep or reject.

Learn

Agent memory, tool design, experiment planning, and how to test which feature helped.

Concrete steps
  1. Start with a plain agent that has the same tools as the baseline.
  2. Add structured notes: what changed, why, expected result, observed result, and next question.
  3. Test one feature at a time: notes, a next-test planner, or repeating a promising result to check noise.
  4. Compare each version against the baseline using the same researcher model, starting conditions, and resource caps.
  5. Count repeat checks and planning calls against the budget. Keep features only if the evidence supports them.
  6. Publish a short report with useful wins, failed ideas, costs, and replay links.
Done when: we can explain which changes helped, hurt, or remain unclear. A win is supported across runs, not one best screenshot.

First release: a working league, our agent, a fair report, and a demo to link from the portfolio.

4

Test on a small task suite

3–5 sessions + GPU runs

Check whether our agent is a better researcher beyond the one setup we built it on.

Build

Versioned tasks with separate development, selection, and final test sets.

Learn

Overfitting: how a system can get good at the test without learning a skill that carries over.

Concrete steps
  1. Add a second small training task, such as a tiny image model, and fresh variants of the language-model task.
  2. Define each task's fixed data, score, allowed edits, and budget before testing agents.
  3. Use development tasks to build the agent and a separate selection set to choose versions.
  4. Reserve untouched task variants and data for the final report. Retire or refresh them after results guide future work.
  5. Keep per-task results visible. Do not blend unrelated scores into a single unexplained number.
Done when: the report separates tasks used to tune the agent from fresh tasks used to judge it.
5

Let an agent improve the agent

5–8 sessions + GPU runs

An outer agent proposes a better research process. The inner agent uses that process to run experiments.

Propose agent change → run task suite → compare → keep or reject → repeat

Build

A bounded self-improvement loop with saved versions, clear budgets, and rollback.

Learn

Search over agent designs, fair checks, and the cost of finding a better agent.

Concrete steps
  1. Start by allowing edits only to the research instructions and note format. Add agent-code edits later if needed.
  2. Let the outer agent inspect development runs and propose one change with a reason.
  3. Evaluate each candidate with the same inner-task budgets. Limit the outer loop to a small number of proposals.
  4. Track the total cost of the search, including rejected agents. Keep the scorer, task rules, and final tests fixed.
  5. Select a candidate using the selection tasks, freeze it, then compare it with the original agent on final tasks.
  6. Repeat the full outer search before claiming that self-improvement works reliably.
Done when: a full improvement cycle works and we can tell whether its gains survive fresh tasks. If not, publish the limit we found.

Call this a bounded self-improvement experiment. It does not imply endless improvement or changes to the frontier model's own weights.

What the platform saves

The recipe

Task, data, code, model, agent, hardware, settings, and seeds.

The work

Ideas, edits, tool calls, training logs, failures, and saved models.

The result

Quality gain, time, GPU hours, API cost, and spread across runs.

Trust rule: an agent may change its solution. It may not change the test or its budget. Gains must beat normal training noise, and final checks use data the agent could not see.

Reuse: models, workloads, scoring, and cost tracking.

Speed lab / kernels

Find one real GPU bottleneck. Write or search for a faster version, then check accuracy.

Reuse: serving load tests and the agent's edit-test loop.

What this shows

A story you can explain

“I built a system that tests how well AI models do research. Then I used it to design and test a better research agent.”

Back it with real results, readable code, and a replay. The contribution is your test design, agent work, and findings.

Scope guard

Keep the first version small

One GPU job at a time. Two researcher models. One training task. One simple run page.

Defer accounts, a large cloud service, many-agent teams, racing, and kernel work until the first fair comparison is complete.
