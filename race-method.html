Can a small decision beat a long plan?

Jev makes one typed choice. Opus and GPT can write whole programmes. This experiment tests whether frequent, inexpensive decisions can navigate well enough to make the trade worthwhile.

Reproduce the experiment and review the evidence →

One turn behind the wheel

  1. Read the road. The model gets text containing JSON: its position, road centreline coordinates, the sector’s exit gate, road width and movement speed. It receives coordinates, not a screenshot.
  2. Choose a plan. It replies with directions and durations. There are nine choices: four directions, four diagonals, or no movement. Legacy plan mode also chooses how long to hold each one; reactive mode fixes the duration at 12 frames.
  3. Drive, then check. The harness runs those keys at 60 simulation frames per second. If the car has not reached the gate, the model gets updated coordinates and feedback about grass, walls and distance remaining.
  4. Save the lap. Positions and headings are recorded 20 times per simulated second. This website replays those positions while you drive. Visiting the page makes no model calls.

What makes a good driver?

This is an arcade navigation task. The car moves instantly in the chosen direction: no acceleration, gears or steering radius. Diagonals have the same total speed as straight moves. Grass slows the car from 170 to 74 screen pixels per second; the treeline pushes it back into the corridor.

A good plan follows a short, clean route, holds each direction for the right duration, and recovers from mistakes. The track is a hand-drawn approximation of the Nordschleife, scaled to 20.832 km across 18 sectors.

For the Opus/Sol plan mode, each turn allows at most 420 planned frames (7 simulated seconds), with 1–240 frames per move. Each sector allows up to five model calls and has a roughly 25-second driving budget. A plan stops early at the gate. The runner advances to the next sector window after its budget is spent even if the gate was not reached.

Would JEV have an advantage?

Jev is TypeSafe AI’s decision model. Its official API returns typed choices, yes/no probabilities and scores. Unlike the current Opus/Sol interface, it does not write an arbitrary driving plan. The blue car is active on the grid. It replays the real trial and stops at 4.99 km with a DNF result.

Selecting among a fixed set of actions is a natural fit for Jev’s Choice interface. But the current task asks for a whole sequence of directions and durations. Choosing “right” is only part of the problem: holding it too long can put the car on the grass.

JSON is just the container. The Opus/Sol response contains actions, not probabilities. Producing valid JSON does not by itself show good spatial planning. Jev’s action probabilities are not measured probabilities of finishing the lap or avoiding a crash; that interpretation would need its own testing.

The new Jev adapter asks for one of the nine directions, uses the returned choice (and logs whether it matches the highest probability), and holds it for 12 frames (0.2 simulated seconds). It then sends a fresh road observation. It allows up to 125 calls per sector, uses the same movement physics and camera as the offline runner, and saves action probabilities plus response times. Each request uses the current state and latest feedback, without a resumed chat history. This is a separate reactive mode: its shorter actions and more frequent feedback mean its times are not a controlled head-to-head comparison with the existing plan-mode recordings. Track A now implements matched action intervals, observation fields and budgets for all three models; transport and reasoning remain configuration differences.

TypeSafe reports fast responses on its own decision tasks; that is not a measured racing result. Faster individual calls could shorten the time needed to generate a recording, although reactive mode makes more calls. It does not reduce the current lap time directly. To test both strengths, report simulated lap time and model response latency separately, alongside completion rate and mistakes. A future real-time mode would need an explicit rule for what the car does while waiting.

How much should you trust the ranking?

Treat this as a playable experiment, not a general intelligence leaderboard. It shows two saved laps on one track, with no repeated-run averages or uncertainty estimates. The legacy replay files preserve positions and summaries, not a complete prompt/response audit. New runs include an audit sidecar.

The human and offline models share the same movement function, but the surrounding conditions differ. Humans see an image and steer continuously; models read coordinates and act in batches. The browser currently cuts immediately to a new sector view, while the offline harness eases its camera. Browser updates use elapsed frame time; the runner uses fixed 1/60-second steps.

The model interfaces differ too: Opus runs through Claude Code, and Sol runs through Codex at xhigh reasoning with an output schema. Legacy runs resume their own session for feedback; matched reactive runs do not. These details matter when comparing results. Matched runs now preserve full run logs. Repeated measurements are still required before making broader claims.
